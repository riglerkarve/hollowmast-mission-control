# MCP gate — 20 August 2026

Recommendation: do not install or build an MCP server this week.

## 1. What would it do better than a `.cjs` tool?

Nothing concrete yet. The current tools already have the properties this workspace needs: a narrow command, named input and output, direct source review, and a handover after the work. The verification suite now separates safe automatic checks from tools that must stay manual. An MCP server would make capabilities discoverable to an agent, but that is not a job outcome; it is another path into the same work.

The missing capability is not a protocol. It is an independently reviewed task with a clear owner. The useful agentic mechanism already present is the role and handover chain: it limits who may interrupt, records what was done, and leaves an absence visible. No MCP feature replaces that.

## 2. What would it cost to keep?

It would be a standing process or integration that can fail when no one is watching. It needs versioning, a launch/restart path, credentials and secret rotation where applicable, a health signal that distinguishes unavailable from healthy, and a way to keep tool permissions from silently widening. It also adds another compatibility boundary between the agent client, the server, and any external provider.

The workspace already has scheduled work whose value depends on honest failure reporting. A server that stops, silently changes its capability list, or is invoked with a different permission set recreates the exact “nothing happened” ambiguity the verification work is intended to remove.

## 3. Where would it sit against the module contract?

Only as a thin facade over one module's existing public API, never as a direct database or filesystem bridge. It would need to obey the existing rules: one route/module owns its tables, another module asks over the API, and every figure has one owner. A generic MCP database tool would bypass all three by allowing cross-module reads and writes outside route validation, provenance, and error shaping.

No present task needs such a facade. The existing `.cjs` tools are clearer because their authority is evident from the command and source file. Adding a protocol before there is a module-scoped operation it uniquely improves would create a capability in search of a job.

## 4. What would it expose?

Mission Control is served on `0.0.0.0` and holds finance, health, wellbeing and credential-adjacent data. A new MCP connection could expose filesystem paths, database rows, tool output, credentials, or a broader command surface to an agent client or an external service. “Local” is not enough: the workspace already learned that a localhost model endpoint can route a request to a cloud model.

An MCP server must therefore be treated as a new door with an explicit data-flow and authentication design, not as a library convenience. No such design is justified by a current use case.

## Decision and re-entry condition

Record **no** for this week. Reconsider only when there is a named repeated operation that a `.cjs` tool cannot perform as clearly, and the proposal names its module owner, exact inputs/outputs, authentication boundary, failure state, and a test that proves it does not expand data access. Until then, roles, handovers, and narrow scripts are the safer and more useful agentic system.
